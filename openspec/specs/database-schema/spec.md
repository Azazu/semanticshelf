# database-schema Specification

## Purpose
What a database migrated to head must look like beyond the behaviour the
storage capabilities already fix: the properties of the schema itself that the
application depends on and that a migration must leave behind, starting with
the names its constraints are filed under.

## Requirements

### Requirement: The schema's constraint names are the ones the application declares

Every constraint on a table the application owns SHALL carry, in a database
migrated to head, exactly the name the application's metadata declares for it.
A name is an interface: migrations drop and alter constraints by name, error
messages carry it, and an operator reads it. A schema whose names differ from
the code's is a trap that no migration tool reports — check constraints in
particular are outside what an autogenerated revision compares — so the match
SHALL be verified against a real migrated database rather than assumed.

#### Scenario: A database migrated to head
- **WHEN** the constraint names of every table the application owns are read
  from the catalog of a database migrated to head
- **THEN** that set equals, name for name, the set the application's metadata
  declares, with nothing extra and nothing missing

#### Scenario: A name the code uses to alter the schema
- **WHEN** a migration or a tool refers to a constraint by the name the
  application declares for it
- **THEN** the database holds a constraint under that exact name

#### Scenario: A constraint keeps its meaning across a rename
- **WHEN** a constraint is renamed to bring the schema in line with the code
- **THEN** what it enforces is unchanged, no row is touched, and a write that
  violated it before still fails afterwards
