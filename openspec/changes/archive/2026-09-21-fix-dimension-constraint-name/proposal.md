# Rename the schema's check constraints to the names the code declares

**Risk-Tier:** medium

## Why

The deployed schema stutters. Nine CHECK constraints carry doubled names —
`ck_assets_ck_assets_source`, `ck_embeddings_ck_embeddings_model_dimension`,
`ck_indexing_jobs_ck_indexing_jobs_status` and six more — because migration
0002 passed names that already began with `ck_<table>_` and the metadata's
naming convention (`ck_%(table_name)s_%(constraint_name)s`) wrapped the
pattern around them a second time. The application declares the short forms,
so code and database disagree about nine names.

That matters for three reasons, none of them cosmetic:

1. `app/db/base.py` exists, in its own words, "so every constraint Alembic
   creates has a name its `downgrade()` can drop". The promise is already
   broken: a future migration that drops `ck_assets_source` by the name the
   metadata renders fails against every real database.
2. A test is green by accident. `tests/integration/test_embedding_storage.py`
   asserts that a bad width raises an `IntegrityError` matching
   `ck_embeddings_model_dimension`, and it passes only because the stuttering
   name happens to contain that substring.
3. ADR-001 records the constraint as `ck_embeddings_model_dimension`. The
   record of the decision and the schema that implements it do not match.

Alembic will never raise this on its own: autogenerate does not compare CHECK
constraints. Verified rather than assumed — a probe revision autogenerated
against the database at head came back with an empty `upgrade()`. So the drift
cannot self-correct; it is repaired deliberately or not at all, and it is
cheapest now, while every database that exists is a development one.

## What Changes

- One Alembic revision renames the nine CHECK constraints to the names
  `Base.metadata` declares. `ALTER TABLE … RENAME CONSTRAINT` touches no data
  and rewrites no table; `downgrade()` renames them back.
- A new integration guard compares every constraint name in a database
  migrated to head with the name the metadata declares, for every table the
  application owns. This is the check that would have caught the defect in
  change 3, and it is the reason to do the work rather than live with the
  names.
- Migration 0002 keeps its current text: it is applied in existing databases,
  and editing an applied migration would make a fresh database and an old one
  disagree about what 0002 did.
- `openspec/ROADMAP.md` row 4a is corrected. It claims an autogenerated
  revision would propose dropping and recreating the constraint; the probe
  above shows autogenerate does not see CHECK constraints at all.

## Capabilities

### New Capabilities

- `database-schema`: what a database migrated to head must look like beyond
  the behaviour the storage capabilities already fix — starting with the rule
  that its constraint names are the ones the application declares.

### Modified Capabilities

None. No requirement of `asset-storage`, `embedding-storage`,
`embedding-models`, `health-probes` or `http-api-conventions` changes: the
rules those constraints enforce are untouched, only the names they are filed
under.

## Non-goals

- Editing migration 0002 or rewriting migration history.
- Renaming anything that is not a CHECK constraint. Primary keys, foreign
  keys, unique constraints and indexes already carry exactly the names the
  metadata declares; this change verified that and leaves them alone.
- Changing what any constraint enforces, or touching a single row.
- Teaching Alembic to compare CHECK constraints (a custom comparator in
  `env.py` is a larger subject than this defect, and the integration guard
  covers the same ground where it matters).
- Any change to the readiness probe, which reads the dimension constraint by
  table rather than by name and is unaffected in either direction.

## Impact

- `alembic/versions/`: one new revision on top of `0002_asset_schema`.
- `tests/integration/`: the name guard, run by `make test-integration` and by
  CI, which migrates a real pgvector database before the marked suite.
- `openspec/specs/database-schema/spec.md`: new capability.
- `openspec/ROADMAP.md`: row 4a corrected and then removed at archive time.
- No application code, no API surface, no dependency, no data.
